## 6.1 设计理由

### 6.1.1 关键决策摘要

| ID | 决策 | 为何 | 舍弃方案 |
|----|------|------|----------|
| D1 | 引擎 Worker 化 | 防 OOM 拖垮 API；引擎可替换 | Gradio 生产、单体 GPU 线程、fork 模型 |
| D2 | ComplianceGateway | 防新接口漏合规 | 仅前端弹窗、仅训练检查 |
| D3 | 统一 Job 队列 | 长任务避免 HTTP 超时 | 同步等待、纯 Cron |
| D4 | 上下文 + 波次 | W1 可交付；MVP+1 不推翻模型 | 按页面拆模块、首版微服务 |
| D5 | 导出单通道 | 满足 100% 合规导出指标 | raw wav 直链 |
| D6 | FastAPI+PG+Redis+OSS | 小团队低学习成本 | Go 双栈、本地盘存音频 |
| D7 | 单 GPU 锁 | 16GB 防并行 OOM | 首周双卡 |

### 6.1.2 与 SRS 原则对齐

| SRS §1.4 原则 | 架构落实 |
|---------------|----------|
| 合规不可砍 | Gateway + 导出单通道 |
| 先闭环再平台 | Core 不含市场 |
| 短剧默认路径 | Production + BatchJob |
| 可运营替代 | Consent 人工审核 |
| 为 MVP+1 预埋 | model_tag、Marketplace 占位 |

### 6.1.3 已知代价

1. 单 GPU → 队列等待（MVP+1 拆 Infer 池）。
2. 强制合规导出 → ffmpeg 队列需监控。
3. 单引擎版本 → 特殊音色 MVP+1 再评估。
4. 单体仓库 → 需 import 纪律 / CI 检查。

## 6.2 架构评审

### 6.2.1 结论

| 项 | 结果 |
|----|------|
| **总体** | **W1 Core 已通过实现验证**；Workflow@W2 待启动 |
| 对齐度 | 与 SRS/宪章高 |
| 可交付性 | Core@W1 ✅（API/Worker/JWT/配额）；W2+ 依赖 BatchJob |
| 风险 | 中：单 GPU 批量；微调 Spike 16GB 已通过，生产素材待调参 |

### 6.2.2 优势

1. 自研/引擎/API/Worker/合规边界清晰。  
2. REQ ↔ 上下文 ↔ 子模块可追溯。  
3. MVP-0 → MVP+1 演进不需推翻 ER。  
4. 合规路径可写集成测试。  
5. 风险在 Spike/§7 已前置。
